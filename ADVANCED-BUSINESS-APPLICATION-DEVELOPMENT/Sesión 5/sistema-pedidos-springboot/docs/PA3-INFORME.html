Consultas JDBC y reportes seguros de pedidos

1. Base, objetivo y alcance

La ampliación permite consultar pedidos por cliente y monto mínimo e identificar clientes frecuentes. Se conserva la aplicación Java 21 con Spring Boot 4.1.1, Spring MVC, JSP, Spring Security, Spring Data JPA y el adaptador HTTP de inventario. Las nuevas consultas se implementan con Spring JDBC. El propósito es ampliar la lectura analítica sin sustituir las operaciones existentes.

La consigna menciona sistema-pedidos-springboot-jdbc-mysql. La inspección del repositorio oficial y de su rama feature/sistema-pedidos-spring-jdbc encontró el proyecto en ADVANCED-BUSINESS-APPLICATION-DEVELOPMENT/Sesión 5/sistema-pedidos-springboot. La referencia remota coincidió con el commit 4edae85a7176f7b2d3525e66e84d336faa5d2eae. Tras comunicar la discrepancia, el estudiante autorizó expresamente esta ubicación. El trabajo permanece en feature/pa3-inca-villagomez.

Separación entre base y aporte PA3

Ya existían el registro y listado JPA, la reserva HTTP de inventario, la búsqueda simple por cliente, el resumen consolidado, los productos más vendidos, sus representaciones JSON/HAL, los roles OPERADOR y CONSULTA y CSRF. También existían veinte pruebas. Estos componentes se reutilizan y no se presentan como aportes nuevos. Aunque JpaRepository proporciona operaciones CRUD, no se encontraron endpoints de edición o eliminación en los controladores.

La PA3 agrega dos consultas parametrizadas, validaciones en Service, dos endpoints REST, un controlador MVC y una JSP de reportes. Amplía la autorización para GET de reportes y añade trece pruebas H2/HTTP, además de una comprobación MySQL optativa. No modifica la entidad ni el contrato del servicio externo de Sesión 4.

Configuración preservada

MySQL continúa como base de ejecución normal y H2 como base de integración automática. Se mantienen las variables externas de conexión y contraseñas. La documentación no agrega credenciales reales. Las comprobaciones no necesitan cambios en otros proyectos, commits ni push.

Este informe tiene cinco secciones con salto de página A4. La carátula y las capturas manuales se adjuntan aparte. Los resultados no observados se identifican como pendientes.

La inyección por constructor conserva responsabilidades explícitas. Los controladores delegan las reglas al servicio; el repositorio ejecuta SQL y materializa los resultados. La primera consulta reutiliza PedidoRowMapper. La segunda devuelve una proyección de repositorio que se transforma en modelo de servicio y DTO de salida.

Búsqueda avanzada

buscarPedidosPorClienteYTotalMinimo(cliente, totalMinimo) usa NamedParameterJdbcTemplate con parámetros :cliente y :totalMinimo. La búsqueda parcial aplica LOWER y LIKE; el monto se filtra mediante total >= :totalMinimo y se ordena por ID descendente. Solo se formatea la lista constante de columnas; los valores del usuario se enlazan. Este uso corresponde al mecanismo de parámetros nombrados documentado por Spring (Spring, s. f.-a).

Clientes frecuentes

listarClientesFrecuentes(minPedidos) agrupa por cliente y utiliza HAVING COUNT(*) >= :minPedidos. COUNT(*) mide pedidos, SUM(cantidad) unidades, SUM(total) importe y AVG(total) ticket promedio. Se ordena por cantidad de pedidos descendente y nombre ascendente. Los importes se conservan como BigDecimal.

La identidad del cliente es el nombre almacenado. No se inventa una entidad Cliente: los homónimos pueden agruparse y las variantes pueden separarse según la collation. La semántica de comodines LIKE se conserva; no se promete coincidencia literal de % o _.

El contexto configurado es /sistema-pedidos. REST usa @RestController y la vista usa @Controller, @GetMapping, Model y el ViewResolver ya configurado. La JSP reside en /WEB-INF/views/reportes-pedidos.jsp y presenta el resumen general, la búsqueda avanzada y los clientes frecuentes. Los formularios GET realizan consultas; no escriben pedidos ni llaman al inventario.

Validación y errores

El servicio rechaza cliente nulo o vacío, monto mínimo nulo o negativo y minPedidos nulo o menor que uno mediante ReporteValidacionException. La API responde 400 con un campo error. Los errores de conversión y parámetros obligatorios ausentes también reciben 400. La vista muestra mensajes controlados y conserva valores válidamente convertidos. Una búsqueda válida sin resultados responde 200 con lista vacía.

Las reglas no se duplican en el controlador. Los atributos se escapan en la JSP, incluidos nombres con caracteres especiales. El formulario de búsqueda requiere cliente y monto; el de frecuencia tiene umbral inicial dos. El resumen se mantiene global, sin atribuirle filtros que el SQL existente no implementa.

Autorización y CSRF

OPERADOR y CONSULTA pueden acceder mediante GET a /reportes/** y a las APIs de reportes. Los anónimos se redirigen al login existente. POST /pedidos permanece exclusivo de OPERADOR. Un token CSRF válido no concede a CONSULTA permiso para registrar; un OPERADOR sin token válido tampoco puede registrar.

Se conserva la protección CSRF predeterminada de Spring Security. La documentación oficial la aplica a métodos inseguros como POST (Spring, s. f.-b). El logout de la nueva vista utiliza POST con token. No se agregan JWT, OAuth2/OIDC ni tablas de usuarios.

La ruta antigua /api/v1/orders conserva su contrato. La PA3 tampoco altera los enlaces HAL del reporte de productos ni rehabilita la URI /api/v1/pedidos/buscar que las pruebas originales esperan ausente.

Resultados registrados

La ejecución con los veinte tests originales pasó. La suite ampliada ejecutó treinta y tres pruebas con cero fallos y cero errores. Una aserción inicial de redirección se corrigió para comprobar exactamente /login. No se ocultó el fallo relajando el estado de autenticación esperado.

Se preparó un test optativo MySQL que usa una tabla temporal de conexión, sin modificar pedidos persistentes. Su ejecución se intentó y falló antes de crear la tabla: el servidor rechazó el acceso del usuario configurado. Por ello no se afirma que las consultas hayan sido ejecutadas satisfactoriamente contra MySQL.

La verificación final con Maven verify terminó en BUILD SUCCESS y generó el WAR: 34 casos registrados, 33 aprobados, cero fallos, cero errores y un MySQL optativo omitido. Los resultados de Maven y empaquetado se registran en README y Surefire. La prueba MySQL se omite por defecto; se activa mediante -Dpa3.mysql=true -Dtest=Pa3MysqlRepositoryTest. La guía PA3-EVIDENCIAS.md contiene pasos, datos esperados y SQL de contraste.

5. Riesgos, entrega y referencias

La combinación JPA/JDBC conserva el esquema existente. Ambas rutas deben mantener los mismos nombres de columnas, tipos monetarios y fecha no nula esperada por PedidoRowMapper. No se cambia ddl-auto=update de MySQL ni create-drop de H2 de pruebas. Los tests H2 no deben ejecutarse contra la base persistente.

H2 ofrece un modo de compatibilidad MySQL (H2 Database, s. f.), pero ello no demuestra equivalencia completa entre motores. Deben verificarse collation, escala de AVG, orden de empates y datos reales. El SQL agregado utiliza funciones comunes; el bloqueo actual es de autenticación MySQL, no evidencia de éxito ni de incompatibilidad SQL.

La reserva remota precede al guardado local. La transacción JPA no revierte una reserva en inventario si después falla MySQL. La PA3 conserva este flujo y no añade reintentos automáticos que puedan duplicar reservas. El listado original /pedidos carga productos del servicio remoto y puede fallar con inventario detenido; la nueva página /reportes/pedidos consulta exclusivamente datos locales.

Las búsquedas no incluyen paginación porque la consigna no la exige. Un volumen alto puede aumentar el tiempo de consulta. LOWER con LIKE y comodín inicial puede limitar el uso de índices. Estas limitaciones quedan documentadas sin introducir migraciones, normalización de clientes o funciones adicionales fuera del alcance.
